# 0.1.2e — Myra initialization-order fix

**Date:** 2026-09-01

## Scope

Runtime correction for the Myra integration after the `0.1.2c` Main Menu migration and `0.1.2d` namespace compatibility correction.

## Fixed

The application could crash while constructing `MyraMainMenuView` with:

`MyraEnvironment.Game is null. Please, set it to the Game instance before using Myra.`

The cause was lifecycle ordering: `ScreenManager` can load a screen before `RailDispatchMonoGame.LoadContent()` establishes the Myra environment.

## Changes

- Initialize the shared `MyraUIManager` at the beginning of `RailDispatchMonoGame.Initialize()`.
- Keep `MyraUIManager.Initialize(this)` in `LoadContent()` as an idempotent safety point.
- Initialize Myra before creating/adding `MainMenuScreen` to `ScreenManager`.
- Preserve the existing `MyraUIManager.Initialize(Microsoft.Xna.Framework.Game)` API.
- Preserve `ScreenManager`, `MenuScreen`, `MenuEntry` and screen lifecycle contracts.
- Keep a single shared Myra `Desktop` and a single Myra render entry point.

## Accelerated integration

The Myra integration now treats the Main Menu as the first production consumer of the shared desktop. Subsequent stages may move additional UI surfaces to Myra without introducing per-screen desktops.

## Stage discipline

`0.1.2a` through `0.1.2d` remain immutable. This stage contains the correction for the runtime failure observed after those stages.
