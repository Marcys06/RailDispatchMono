# 0.1.5e — Coupling command controls

**Data:** 2026-09-03

## Cel

`0.1.5e` adds the first direct gameplay command layer for the rigid coupling model. The command layer intentionally uses the existing `TrainManager` and `CouplingService` instead of introducing a second coupling implementation.

## Sterowanie

- `C` — `Coupling`: executes coupling against the nearest valid boundary-end candidate.
- `X` — `Decoupling`: first tries to decouple the last coupling created by `C`; if that reference is unavailable, it uses the first remaining runtime coupling.
- `F6` — coupling/shunting speed profile `3 km/h`.
- `F7` — coupling/shunting speed profile `4 km/h`.
- `F8` — coupling/shunting speed profile `5 km/h` (default).

The command only executes coupling when both participating trains are already at or below the selected shunting speed. The authoritative geometric, boundary, alignment, occupancy and coupler checks remain in `CouplingService`.

## Semafor

The command layer identifies `SignalAspect.Reserve3` (`S14`, `Rezerwowy 3`) as the semantic signal aspect associated with coupling/shunting. This milestone does **not** change the existing signal aspect's global speed value or add new signal physics.

## Behavior

A successful `C` command:

1. selects the closest valid candidate from `GetCouplingCandidates()`;
2. verifies the selected 3/4/5 km/h command limit against both train speeds;
3. delegates the actual operation to `CouplingService.Couple()`;
4. retains a reference to the concrete runtime coupling so `X` can target it;
5. leaves the merged consist under the existing rigid coupling and RadioStop behavior.

A successful `X` command delegates to `CouplingService.Decouple()`, so the concrete vehicle-end connection still determines the split point and resulting vehicle order.

## Scope boundary

This is a command layer, not the final vehicle-selection UI. The current `C` command automatically chooses the nearest valid candidate because the visual vehicle/end selection mechanism is still planned separately. The command layer does not add coupling slack, impact forces, coupling delay, brake-pipe propagation or longitudinal dynamics.

## Verification

No live gameplay test was executed in this change session. The implementation was kept within existing compile-time types and APIs; runtime verification remains dependent on the user's working .NET/MonoGame environment.
