# 0.1.4a — Train and semaphore mechanics

## Trains

- Train compositions no longer render all vehicles at the head position when spawned.
- Vehicle positions at spawn use the existing train geometry/composition spacing instead of the empty trajectory fallback.
- Train collision checks now use the same spaced vehicle positions, so a spawned composition occupies multiple grid cells when its physical length requires it.
- Spawn collision checks also use the complete vehicle composition rather than only the head position.

## Semaphore speed control

- Added a persistent per-train semaphore speed state.
- A semaphore is tracked by its `Signal` identity, not by its grid cell. Multiple signals in one cell for different directions therefore remain independent.
- The speed limit from a semaphore becomes the train's persistent limit only after that semaphore has been passed.
- `Clear` does not allow acceleration before the semaphore is passed.
- After passing `Clear`, the train may return to its physical `Vmax`.
- After passing a restrictive aspect such as `Speed40`, that limit remains active until another semaphore replaces it.
- `Stop`/`StopStation` remain handled by the existing train braking and block/signal systems; the new persistent-limit layer does not create a second stop controller.
- Station stopping remains authoritative through `StationController`; its braking/dwell actions can reduce speed below the semaphore-derived limit without being overwritten by the semaphore system.

## Architecture

- `TrainSignalSpeedState.cs` bridges the new persistent limit state into the existing `Train` acceleration/braking implementation.
- `TrainManager` owns per-train semaphore sequencing because it already coordinates train, collision, station and block systems.
- Existing signal aspects and physical vehicle `MaxSpeed` values remain the source of speed-limit values; no second `Vmax` constant was introduced.
