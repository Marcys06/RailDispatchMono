# 0.1.6a — Documentation baseline and passenger-system audit

**Date:** 2026-09-04  
**Status:** development stage

## Purpose

`0.1.6a` establishes the documentation baseline for the new 0.1.6 development line. No new gameplay feature is claimed by this stage. The goal is to align the maintained documentation with the implementation completed through `0.1.5pre` and to explicitly document the station/passenger foundation already present in Core.

## 0.1.5 state carried into 0.1.6

The following are treated as implemented contracts rather than future work:

- rolling-stock catalogue and Depot-based train creation;
- consist mass-dependent acceleration/braking and power-dependent Vmax;
- speed-aware signal stopping and RadioStop safety;
- rigid runtime coupling/decoupling through `CouplingService`;
- fixed `6 km/h` coupling limit;
- `X` decoupling of a wagon under the cursor below `6 km/h`;
- `F6` manual shunting toward `3 km/h` for the train under the cursor;
- `F7` direction reversal at `0 km/h` without reordering or repositioning the consist;
- rigid vehicle spacing and trajectory-based curve following;
- per-vehicle curve orientation derived from the vehicle's own position on the travelled trajectory;
- runtime train diagnostics and current save compatibility rules.

## Station foundation

`Station` and `StationController` are existing domain components. A station has world geometry plus stop/dwell and passenger-generation parameters. `StationController` owns station collection, stop/dwell coordination, generation timers and station-service invocation.

Train station service is guarded by station-visit state so a train is not serviced repeatedly while remaining inside the same station area.

## Passenger foundation

The existing `Game/Passengers` subsystem provides:

- `Passenger` with fixed origin/destination;
- `PassengerState` with `WaitingAtStation`, `OnBoard` and `Arrived`;
- `PassengerManager` for active passenger state and boarding/alighting;
- `IPassengerService` and `DefaultPassengerService` for station exchange;
- `IPassengerDemandProvider` and `RandomPassengerDemandProvider` for destination demand.

`Wagon` owns its boarded passenger list and enforces passenger capacity and service-route acceptance.

The current operational flow is:

`Station → generation → waiting → train arrival → alighting → boarding → dwell → departure`.

`DefaultPassengerService` performs alighting before boarding. Passenger exchange can produce floating-text feedback.

## Passenger scope boundary

The following are intentionally not implemented yet:

- transfers;
- timetable-aware passenger choice;
- competition between trains for demand;
- population/city-based demand;
- fares and revenue;
- passenger satisfaction/wait-time scoring;
- passenger-specific behavioural classes;
- persistent passenger state;
- visual platform crowds.

The random demand provider is a replaceable placeholder, not the final passenger-demand model.
