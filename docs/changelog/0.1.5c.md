# 0.1.5c — Coupling candidate discovery

**Data:** 2026-09-03

## Coupling / decoupling mechanics

- Added `CouplingCandidate` as a UI-neutral snapshot of a possible physical connection.
- Candidate data contains both train/vehicle/end references, both calculated endpoint positions, measured distance and the authoritative `CouplingCheckResult`.
- Added `TrainManager.GetCouplingCandidates(Train)` as the single discovery entry point for future UI and input code.
- Candidate discovery considers only outer vehicle ends, matching the current rigid coupling rule.
- Candidate validation is delegated to `CouplingService`; UI code does not need to duplicate compatibility, distance or alignment rules.
- Candidates are sorted by endpoint distance to provide deterministic selection order.

## Scope

This stage does not add UI, input bindings, persistence or coupling physics. The candidate API is intentionally a mechanics-facing contract that can be consumed by those layers later.
